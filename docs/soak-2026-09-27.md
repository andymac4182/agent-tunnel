# Soak, load, chaos and fairness re-run (2026-09-27)

Task rows M6-C176 and M6-C150. This re-runs every experiment in
[soak-2026-09-26.md](soak-2026-09-26.md) on a head that contains the fixes made
since: `TCP_NODELAY` (M6-C124, M6-C163, PR #195), the device staying online under
load (M6-C151, M6-C159, M6-C160, PR #199), and the soak harness's MCP session
accounting (M6-C146, PR #203). The 2026-09-26 document is kept as measured, as the
record of the builds it measured. Where its figures are superseded, it now
points here.

These are **measurements, not service levels.** The same limits apply as before.
Each experiment ran on one 4-vCPU GitHub runner that hosted the relay, the Redis
TLS forwarder, the devices and the Python load generator together. It used one
device (two for fairness) and one tenant. Neither the 20 users × 5 devices case,
the 100 devices over 24 hours case nor the 1 GiB transfers in
[testing.md](testing.md#soak-chaos-and-load-experiments) were run.

**Steady state between faults:** echo p50 5.8 -- 7.4 ms and p99 8 -- 12.5 ms;
MCP p50 5.6 -- 7.4 ms and p99 8 -- 13 ms. This replaces the 2026-09-26 steady
state of about 65 ms (run 36168189990), which was the quantum. Each run had 7 device sessions
and 0 rotations. Chaos is too short to cross a 300 s rotation.

**No silent replay and no fake success,** measured again in both runs:

* 0 integrity mismatches.
* MCP backend invocations were 3,117 and 3,089, exactly the consumer-visible
  successes (3,116 and 3,088) plus one warm-up. No request reported as unknown
  or refused executed, and nothing ran twice.
* Every non-success carried an explicit code and execution class. The
  exceptions are the 6 transport-level `CONN_ConnectionResetError` rows during
  the relay restart and the MCP `-32600` rows below.

**What changed for MCP during outages.** An MCP call to an offline device is
now answered `DEVICE_OFFLINE`/not_dispatched, like echo: 0 `NOT_FOUND` in either
run. On 2026-09-26 it was `NOT_FOUND` (M6-C123). This re-run did not attribute
which change did it. After each fault that ends the device session, each probe
worker's first call on its old MCP session got HTTP `404` with JSON-RPC
`-32600`: 2 per fault, 12 per run. The device's MCP child and its sessions
end with the device session, and a `404` on an unknown session is the MCP
transport's signal to re-initialise. The harness does re-initialise: the pool
counts the forgotten session, and the next call succeeds. These are therefore
expected session losses, not errors of the product. No probe session was left
open at shutdown: neither run emitted an `mcp-session-leak` event.

* **The shared-device collapse is gone.** B keeps 99% of its requests on the

  ended: one start per device and no `DEVICE_OFFLINE`. A's only refusals are the
  listener's `CONNECTION_LIMIT` (about 28,000 per flood phase) and one 0.5 s
  rotation freeze. B's 6 refusals fell in that freeze window, where A's workers
  fill the device's 8-request hold. There is still no per-user share of one

  unfairness small but not zero.
* **A flood on another device still raises B's latency 16×.** B's p50 went from
  4.8 ms to 77 -- 81 ms, and its p99 from 6 ms to 109 -- 120 ms, on a device A
  never touched (M6-C183). Before the quantum was removed, this was hidden
  inside the 41 ms baseline.

## 6. M6-C181 attributed and fixed (M6-C190)

Branch `fix-c181`, measured 2026-09-27 on hosted `ubuntu-latest` (4 vCPU),
`experiments=load`, `load_args="--kinds mcp --steps 16,32,48,64,96,128"`.
Each run's artifact carries `http-failures.jsonl`, the payload-free
failed-exchange lines the harness extracts from the relay and device logs.

**Mechanism (measured).** The relay's bounded 128-slot data writer queue to
the device filled for a moment during bursts of new exchanges. The owner
actor refused the next `http-forward/1` chunk as `REVERSE_CHANNEL_UNAVAILABLE`,
the ingress's outbound pump ended without sending the device anything, and
the device held a truncated request until one of its own budgets expired. On
branch `fix-c181-diag-baseline` (the diagnostics with the fix disabled; run
**36268148099**, AMD EPYC 7763, the CPU of the original runs), **173 of 173**
failed MCP calls had a refused write with that code. Which part of the
request was missing decided the outcome:

| Missing at the device | Device budget | Consumer saw | Calls |
| --- | --- | --- | --- |
| the request HEAD | first HEAD, 10 s | `HTTP_DEADLINE_EXCEEDED`/`not_dispatched` after ~10 s | 54 |
| part of the BODY record | record, 10 s | `HTTP_DEADLINE_EXCEEDED`/`dispatched` after ~10 s | 37 |
| END (and FIN) | operation deadline, 30 s | `HTTP_DEADLINE_EXCEEDED`/`dispatched` after ~30 s | 78 |
| (same, carrier ended first) | -- | `HTTP_STREAM_INTERRUPTED`/`unknown` after ~30 s | 4 |

The p99 stayed low because only the calls whose chunk was refused stalled;
every other call on the same sessions completed. Each burst of failures
started within milliseconds across different sessions, because a stall of
the writer released many closed-loop workers at once. It was not the
harness's shared sessions, the stdio export, credit or admission.

**No refused call reached the MCP child.** In all 173 the device's record
shows `request_ends` = 0 and no request FIN. The stdio export reads the whole
request body, which ends only at FIN, before it writes to the child, so no
`tools/call` was delivered to the tool. The `dispatched` label is the
bridge's conservative one: its handler had started, not the tool.

**Fix.** A chunk the writer queue refuses only because it is full now parks
at the head of the stream's bounded FIFO and is retried in order after every
actor command and on the tick. A chunk parked before the owner's FIN is still
sequenced ahead of it (M6-C191). A write the actor still refuses resets the
stream, so the consumer is answered promptly with `HTTP_STREAM_INTERRUPTED`
(`unknown`) instead of after 10 -- 30 s. See
[http-forwarding.md](http-forwarding.md) ("Full writer queue").

| Run | CPU | `HTTP_DEADLINE_EXCEEDED` (steps 16 -- 128) | Other non-capacity errors | Writer parks |
| --- | --- | --- | --- | --- |
| 36268148099 (fix disabled) | EPYC 7763 | **169** (32: 7, 48: 36, 64: 40, 96: 55, 128: 31) | 4 `HTTP_STREAM_INTERRUPTED` | (no counter) |
| 36268153009 (fix) | EPYC 9V45 | **0** | 0 | (no counter) |
| 36268804984 (fix) | Xeon 8573C | **0** | 1 `HTTP_STREAM_INTERRUPTED`, 5 ms | (no counter) |
| 36268810145 (fix) | EPYC 9V45 | **0** | 0 | (no counter) |
| 36269568242 (fix) | EPYC 7763 | **0** | 1 `HTTP_STREAM_INTERRUPTED`, 5 ms | 41,379 |
| 36269573286 (fix) | EPYC 7763 | **0** | 0 | 31,349 |

The two runs on the baseline's CPU parked tens of thousands of chunks, so the
path was exercised, not avoided by faster hardware. The two remaining
interrupted calls were answered in about 5 ms: their stream was released
(`closed`, nothing sequenced) while its first chunk was parked, and the parked
write failed as `REVERSE_CHANNEL_INTERRUPTED`. What released those two
streams is not attributed (M6-C192).

**Cost, same CPU (7763), fix vs. fix disabled.** From 16 to 48 workers,
throughput is unchanged within 4% (717 -- 733 / 840 -- 853 / 854 -- 863 vs.
745 / 845 / 838 OK/s).
At 64 workers the calls that used to fail now wait for the writer: the p99
rises from 94 to 191 -- 194 ms, OK/s falls from 794 to 672 -- 686, and
`ADMISSION_LIMIT` refusals rise from 313 to 1,326 -- 1,514, because waiting
exchanges hold their admission permits. At 96 and 128 workers OK/s rises from
519 / 498 to 590 -- 592 / 569 -- 577. This is the queue's backpressure made visible
as latency instead of as 10 -- 30 s failures; its 64-worker cost is recorded
in M6-C192.
