# Milestone task tracker

Last updated: 2026-09-12T05:12:20+10:00

This tracker follows the roadmap. It records implementation work, discovered defects, owners, exact acceptance scope, and the evidence needed to close each gate.

Status values are deliberately narrow:

- verified local: the stated scope passed at its recorded revision or baseline; this does not
  imply hosted CI, production readiness, or a broader milestone gate.
- implemented awaiting verification: source changes exist and a focused
  result or component path exists, but the required rerun or wider scope is
  still open.
- in progress: active implementation or an active integration run remains.
- planned: not started.
- blocked: cannot close until the named prerequisite or external dependency
  changes.

The milestone summary is a gate view, not a count of checked boxes. A
milestone remains open until every required task has evidence at its declared
scope.

M1 and M2 summary statuses preserve the historical local baselines stated in
their evidence documents and are intentionally narrower than the current
rerun rows. M1-01..03 and M2-01..04 describe those dated baseline results;
M1-04, M1-05, M2-05 and M2-06 track current or broader work. A later code,
fixture, authorization, or harness change does not erase a historical result,
but it does keep the affected current row open until its exact command and
scope are rerun.

## Completion timing

`Completed at` is the time the row's full stated acceptance scope was verified,
not the time coding finished or an estimate of future completion. Record new
completions as ISO 8601 timestamps with seconds and an explicit offset, using
Australia/Brisbane (`+10:00`), in the same update as status and evidence. Open
rows use `—`. Milestone timestamps require the full milestone gate to pass.

Historical dates come from [m1-harness.md](m1-harness.md),
[m2-verification.md](m2-verification.md), and
[m7-verification.md](m7-verification.md). `time not recorded` means only the
date is known; it must not be treated as midnight or included in hourly rates.
Use `unknown (historical)` if no completion date can be established. The
baseline below was observed when timing was added; it does not date those
historical completions or assert that current reruns passed.

Append each new task, first completion, reopening, and re-verification to
[Completion history](#completion-history), with its stable ID and evidence.
On reopening, preserve the previous completion in history and clear the row's
`Completed at`; on re-verification, record a new timestamp. Keep history
append-only, recording corrections as new events. Count first completions
separately from re-verifications to measure tasks completed per hour/day;
reopenings reduce net completion and new tasks increase scope. These timestamps
measure completion throughput, not hands-on effort or test execution duration.
Apply the same rules to the [edge-case matrix](m7-edge-cases.md#completion-history).

## Updating rules

1. Add a stable-ID task when a defect, implementation slice, or missing test is
   discovered, before implementing it. Put the current owner and the exact
   acceptance scope in the same change.
2. Record the exact command, fixture, revision, and evidence document for every
   verified-local status. A component test cannot close a cross-relay,
   process-lifecycle, Redis-authority, adapter, release-artifact, or VM task.
3. After networking, authorization, fixture, dependency, or protocol changes,
   demote affected tested rows to implemented awaiting verification until the
   required commands are rerun. Do not promote a stale result.
4. Keep M1/M2 historical local results tied to their stated date and scope.
   Hosted CI, production readiness, and alpha status require separate evidence
   and must never be inferred from those local results.
5. Use in progress only for work actively being implemented or run. Use
   blocked only when a named prerequisite or external dependency prevents
   progress; record that blocker in the acceptance column.
6. A milestone checklist is complete only when all required rows are verified
   at their declared scope and its linked evidence is current. Keep edge-case
   coverage in [m7-edge-cases.md](m7-edge-cases.md) and link the relevant stable
   task IDs here.
