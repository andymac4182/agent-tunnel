# Soak, load, chaos and fairness measurements (2026-09-26)

Task row M6-03. These are **measurements, not service levels.** Every number
below comes from one small host running the relay, the Redis TLS forwarder,
the devices and the load generator together. Nothing here is a throughput,
latency or availability claim for any other host, for a deployment, or for
the Fly relay. The proposed workloads and targets in
[testing.md](testing.md#soak-chaos-and-load-experiments) are still
unmeasured at their stated sizes: 20 users × 5 devices, 100 devices for 24 hours,
and 1 GiB transfers were **not run**.

## What was run, and where

**Product under test.** Release binaries (`cargo build --release --locked`)
built from `origin/main` at `6830ba79` (PR #161). The hosted runs built the same
product source from the probe branch `m6-03-soak-run`, which differs from
`6830ba79` only in `scripts/` and `.github/`. The local binaries' sha256 values are
in the logs directory (`bin-sha256.txt`).

**Harness.** `scripts/m6-soak.py` (subcommands `soak`, `load`, `chaos`,
`fairness`, `flood`), sequenced by `scripts/m6-soak-all.sh`, and on a hosted
runner by `.github/workflows/m6-soak.yml`, which runs manually only. Each run
brings a stack up from an empty Redis namespace with the shipped commands the
operator guide uses (`credentials create`/`import`,
`activate-first-incarnation`, `provision-catalog`, `add-user`, `add-device`,
`add-service`, `set-grant`, `serve`, `connect --json`). Every consumer request
goes consumer → relay → device over real TLS sockets, and none bypasses the
relay. The workloads are:

* echo: `POST /v1/devices/{d}/services/{s}/echo` with a 1 KiB generated payload.
  A request counts as successful only if the reply is byte-exact (canary +
  payload), so a wrong or cross-wired reply is an error (`INTEGRITY_MISMATCH`).
* MCP over http-forward (`mcp-2025-11-25`): each worker runs one MCP session
  with `initialize`, then `notifications/initialized`, then repeated
  `tools/call echo`. The call is backed by the repository's MCP fixture on the
  device. A call counts as successful only if its per-call marker comes back.
  The fixture logs every invocation it executes, so the harness can compare
  **side effects executed on the device** with **successes the consumer
  saw**.
* One keep-alive HTTP/1.1 connection per worker. A request that the harness
  itself cannot complete is recorded as `CONN_*` or `CLIENT_TIMEOUT` and is
  never retried.

**Raw data.** Each run directory holds `requests.csv` (one row per request:
time, kind, worker, phase, latency, HTTP status, error `code`/`execution`,
integrity), `samples.csv` (relay/device/forwarder RSS and file descriptors,
the relay's metrics gauges, and the host 1-minute load, every 5 to 15 s),
`events.jsonl`, `summary.json` and `run.txt`. Hosted artifacts:
`m6-soak-metrics-*` of runs 36159173753, 36168189990 and 36197764844
(7-day retention; synthetic metrics only, with no relay or device logs). Local runs are
under `/private/tmp/claude-501/m6-03-soak-logs/` on the maintainer Mac.

## 2. Load (hosted, run 36168189990)

Closed loop: N workers each send the next request as soon as the last one
is answered. Each step lasts 30 s. Echo steps ran first, then MCP steps, with
one device and the default limits (client `max_streams = 64`, relay
`max_pending_operations_per_owner = 64`, `max_streams_per_device = 64`).

| Echo workers | OK/s | p50 ms | p95 ms | p99 ms | Errors (by code) |
| --- | --- | --- | --- | --- | --- |
| 1 | 23.6 | 42.5 | 43.2 | 43.8 | 0 |
| 2 | 24.5 | 82.0 | 82.6 | 83.0 | 0 |
| 4 | 48.9 | 82.0 | 82.7 | 83.3 | 0 |
| 8 | 97.1 | 82.7 | 84.5 | 87.0 | 0 |
| 16 | **191.6** | 84.9 | 91.3 | 93.4 | 0 |
| 32 | 142.7 | 55.7 | 94.7 | 105.6 | 57,943: `DEVICE_OFFLINE` 57,739, `REVERSE_CHANNEL_INTERRUPTED`/unknown 154, `DEVICE_REJECTED` 50 |
| 48 | 8.9 | 41.1 | 95.8 | 97.2 | 82,520, mostly `DEVICE_OFFLINE` |
| 64 | 6.2 | 50.0 | 59.7 | 65.7 | 87,745, mostly `DEVICE_OFFLINE` |
| 96 | 0.0 | -- | -- | -- | `DEVICE_OFFLINE` 56,808, connection resets 24,632 |
| 128 | 5.5 | 79.2 | 98.3 | 99.9 | `DEVICE_OFFLINE` 45,186, connection resets 31,410 |

* **Knee: 16 concurrent echoes, about 190 OK/s on this runner.**
* **The first refusal is not a capacity refusal.** At 32 workers, half the
  configured stream budget, the first errors are `DEVICE_OFFLINE`: the
  device's session ends and the device reconnects (task row M6-C120). The
  documented capacity codes (`ADMISSION_LIMIT`, `STREAM_LIMIT`,
  `QUEUE_BUDGET_EXCEEDED`) never appear for echo. Above the knee, throughput
  collapses instead of plateauing.
* Latency is quantized. The p50 is 42.5 ms with one worker, and 82 ms with 2 to 16
  workers, where per-worker throughput halves. Loopback round trips should be
  well under 1 ms. See M6-C124.
* In-flight requests cut by a session end are answered
  `REVERSE_CHANNEL_INTERRUPTED` with `execution=unknown`, which is an explicit
  ambiguous outcome and not a success.

| MCP workers | OK/s | p50 ms | p99 ms | Errors (by code) |
| --- | --- | --- | --- | --- |
| 1 | 7.2 | 45.0 | 84.0 | `NOT_FOUND` 11,406: this step began while the device was still reconnecting after the echo-128 step |
| 2 | 26.6 | 83.9 | 125.1 | 0 |
| 4 | 39.6 | 89.0 | 130.0 | 0 |
| 8 | 8.4 | 127.1 | 131.7 | JSON-RPC `-32603` 1,811 (M6-C122) |
| 16, 32 | 0 | -- | -- | JSON-RPC `-32603` on every call |
| 48 -- 128 | 6.7 -- 35.5 | 83 -- 122 | 203 -- 327 | `-32603`, `NOT_FOUND`, connection resets, `HTTP_STREAM_INTERRUPTED`/unknown, and at 64 workers **102 `ADMISSION_LIMIT`**, the only documented capacity refusal the run produced |

Relay during the load run: RSS 17.5 → 29.0 MiB at peak, 28.6 MiB at end;
at most 85 open descriptors, falling back after the steps; at most 62 relay streams
and 14,962 queue bytes, both 0 at end. Device RSS rose from 8.5 to 15.7 MiB,
with at most 51 descriptors.

**Limits.** This was a single device and a single runner. The load generator is Python
(asyncio, one process) on the same 4 vCPUs. At high worker counts, some
of the collapse could be CPU contention between the generator and the relay,
but the session ends are reported by the device itself (see M6-C120, which
reproduces them with the generator at about 5 -- 15 load on a 10-core host).

## 3. Chaos (hosted run 36168189990, repeated in 36159173753 and locally)

Probes: 4 echo workers and 2 MCP workers, each sending a request every 100 ms,
through every fault. Twenty seconds of steady traffic separate the faults.
Recovery is the time from the end of the fault to the end of the first successful
echo that **started** after it. After a device kill, the harness restarts `connect`
after 1 s, standing in for a service manager.

| Fault | Recovery (hosted 2nd run / hosted 1st run / local) | Outcome of affected requests |
| --- | --- | --- |
| `connect` SIGKILL, restart after 1 s | 0.09 / 0.10 / 0.22 s after restart | echo `DEVICE_OFFLINE`/not_dispatched; MCP `NOT_FOUND`/not_dispatched, one `HTTP_STREAM_INTERRUPTED`/unknown |
| `connect` SIGTERM, restart after 1 s | 0.05 / 0.05 / 0.17 s after restart; exit 0 within 16 ms | same classes, plus one `REVERSE_CHANNEL_INTERRUPTED`/unknown |
| SIGSTOP 10 s | 0.74 / 1.06 / 0.66 s after SIGCONT | The relay ends the session even for 10 s. The device reconnects by itself and **never exits** (the M6-C105 fix holds). In flight: `REVERSE_CHANNEL_INTERRUPTED`/unknown (echo), `HTTP_STREAM_INTERRUPTED`/unknown (MCP) |
| SIGSTOP 40 s | 0.56 / 0.98 / 0.72 s | same |
| SIGSTOP 70 s | 0.75 / 0.82 / 1.01 s | same |
| Redis `docker pause` 5 s (dedicated container on the runner) | **43.4 / 24.4 s** / not run | `DEVICE_OFFLINE` for the whole window, 8 `AUTHORIZATION_UNAVAILABLE`/not_dispatched during the pause (M6-C125) |
| relay SIGKILL, restart at once | 45.1 / 25.9 / 41.9 s after listening | `DEVICE_OFFLINE`, connection resets. This is the documented owner-lease wait (up to 30 s after a SIGKILL) plus the reconnect backoff ([runtime.md](runtime.md#reconnecting-connect)) |

The Redis pause did not run locally: Docker Desktop on the Mac could not create
containers that night, and the shared Redis is never paused. It ran on both
hosted runners against a `redis:8.4.0-alpine` container that the run started
itself (`appendfsync always`, `redis_restart_continuity_seconds = 1`).

**No silent replay and no fake success,** measured in every chaos run:

* 0 integrity mismatches, so no 200 carried a wrong or foreign body.
* MCP side effects executed by the device's backend were 2,018 (2nd hosted),
  2,013 (1st hosted) and 2,369 (local). In each case that is exactly the
  consumer-visible successes plus one warm-up call. Every request reported
  `unknown` or refused was **not** executed, and nothing ran twice.
* Every non-success carried an explicit code and execution class
  (`not_dispatched` or `unknown`). The only exceptions are the transport-level `CONN_*`
  rows during the relay restart, where the socket itself died.

## 4. Fairness (hosted run 36168189990)

Two users in one tenant, because this alpha does not support a second tenant
(operator.md). User A floods with 128 closed-loop echo workers. User B sends 2 × 5
req/s. Each phase lasts 60 s. The run has two variants: B targets **its own device**, then B targets
**the device A floods** (B holds a grant on it).

| Phase | B success | B p50 / p99 ms | A success/s |
| --- | --- | --- | --- |
| baseline, B's own device | 600 / 600 | 41.0 / 47.0 | -- |
| **flood, B's own device** | **600 / 600** | 74.3 / 109.1 | 30.0 |
| recovery, B's own device | 600 / 600 | 7.8 / 47.0 | -- |
| baseline, shared device | 600 / 600 | 10.8 / 47.3 | -- |
| **flood, shared device** | **24 / 596** (568 `DEVICE_OFFLINE`, 4 `REVERSE_CHANNEL_INTERRUPTED`/unknown) | 83.3 / 279.3 | 36.0 |
| recovery, shared device | 332 / 600 (268 `DEVICE_OFFLINE` while the device reconnects) | 7.0 / 47.4 | -- |

* On separate devices, B kept every request while A flooded. B's p99
  rose from 47 to 109 ms. The first hosted run showed the same shape: 600/600, p99 47.8 → 121.7 ms.
* On a shared device, A's flood takes the device's session down (M6-C120), and
  B loses about 96% of its requests. There is no per-user share of one device's
  capacity (M6-C126).
* In the local run of the same experiment, the flooded device's `connect`
  **exited** with the terminal `PROTOCOL_ERROR` "STREAM_FORGET connector
  sender evidence is incomplete" after its third flood-induced session end.
  The device then stayed offline for the rest of the run (M6-C121).

## 5. Flood reproduction (local, 3 runs)

`scripts/m6-soak.py flood --workers 128 --seconds 60`: one device, 128
closed-loop echo workers for 60 s. The runs were at host load 6.7 -- 14.9, so their
timings are not used.

| Run | Device session ends in 60 s (all `RESOURCE_EXHAUSTED` "bounded connector queue limit reached") | OK / requests | Answered after the flood (10 probes) | `connect` exited |
| --- | --- | --- | --- | --- |
| `e2ce22185a16` | 5 | 23,974 / 200,886 | 7 / 10 | no |
| `128f26a99c17` | 4 | 29,591 / 196,173 | 10 / 10 | no |
| `ccf378ea0693` | 5 | 24,063 / 202,120 | 3 / 10 | no |

Every run produced `DEVICE_OFFLINE` and `DEVICE_REJECTED` (not_dispatched),
136 -- 160 `REVERSE_CHANNEL_INTERRUPTED`/unknown, and about 122,000 consumer
connection resets, the relay closing consumer connections under the flood.
The terminal exit of M6-C121 did not recur in these three runs.

## Defects and findings filed

| Row | Finding | Evidence |
| --- | --- | --- |
| M6-C120 | A consumer flood ends the device's session (`RESOURCE_EXHAUSTED`, connector queue limit) instead of being refused at relay admission; every user of the device then sees `DEVICE_OFFLINE` | load step 32 (hosted); flood 3/3 runs; fairness shared-device phase |
| M6-C121 | Once, `connect` exited terminally (`PROTOCOL_ERROR` "STREAM_FORGET connector sender evidence is incomplete") after flood-induced session ends, so the device was left offline for good | local fairness run `4cfb0875d6fe`; 1 of 4 flooded `connect` processes observed |
| M6-C122 | MCP `tools/call` returns JSON-RPC `-32603` from 8 concurrent MCP sessions on one device | hosted load, MCP steps 8 -- 128 |
| M6-C123 | During a device outage, the http-forward route answers `NOT_FOUND`/not_dispatched where echo answers `DEVICE_OFFLINE`; an MCP client cannot tell "offline, retry" from "no such service" | every hosted chaos fault; MCP load step 1 |
| M6-C124 | Request latency is quantized near 40 ms on Linux loopback (one worker p50 42.5 ms; 2 -- 16 workers 82 ms), and the relay and client set `TCP_NODELAY` nowhere except the membership runtime | hosted load and chaos steady state; code search. Mechanism not measured |
| M6-C125 | A 5 s Redis pause ends the device session; echo is unavailable for 24 -- 43 s after Redis resumes | hosted chaos, 2 runs |
| M6-C126 | There is no per-user fairness on a shared device: user B's success rate on a device user A floods falls to 4% | hosted fairness, 2 runs |
