Client exit codes

The implemented tunnel-client mapping distinguishes operator actions. Read the diagnostic alongside the process status.

ExitMeaningOperator action
0Success or orderly stopNo action required.
1Unexpected protocol, supervisor or signal failureInvestigate a defect or version mismatch.
2Invalid invocation or configurationCorrect the command or profile.
3Credential failure or stale authorizationRead the cause: credential refusal is terminal; stream authorization expiry may reconnect.
4Transport failure or closed sessionCheck reachability and reconnect policy.
5Deadline exceededCheck latency and the configured bounded deadline.
7OWNER_BUSY or RESOURCE_EXHAUSTEDCheck ownership, capacity and reconnect limits; this does not resolve earlier operation outcomes.
130Cancellation before orderly completionInspect interruption state; an orderly live-session stop returns 0 instead.

With reconnect enabled, retryable failures normally produce lifecycle events rather than process exits. A finite attempt limit, disabled reconnect or terminal cause ends the process with the last cause's status. Do not infer operation completion from a reconnect or an exit code.

Exit 6 is reserved for unknown outcomes but has no producer in the current client. Do not rely on receiving it to detect every ambiguous effect. Client exit 130 also covers a second stop request and a drain timeout. The relay does not otherwise use this table: it returns 0 or 1, plus 130 for an interrupted serve or an abandoned writing command. Local doctor independently returns 0, 2 or 3.

Configuration rejected

Use client config check or relay check-serve-config, not the legacy bootstrap schema checker. Check unknown fields, endpoint scheme, namespace characters and rotation timing. A dry run does not verify referenced files.

Certificate or connection failure

Run local doctor. Check the device key/certificate pairing, expiry and CA trust; verify the relay hostname and mTLS listener. Do not bypass validation or swap in test credentials.

A device-identity refusal during control registration is now a non-retryable CREDENTIAL_ERROR, exit 3: check the profile device UUID, certificate SAN and catalog registration rather than repeatedly reconnecting. The response deliberately does not reveal which identity check failed. A catalog credential that is not yet valid remains a retryable transport error. The cluster's earlier unknown-key lookup can still close without this refusal reason and appear as TRANSPORT_ERROR; do not assume every identity failure is classified.

Operational surfaces

No metrics endpoint, audit log, client status command or network doctor is supplied in this alpha. Relay logs go to stderr; retention and rotation are external responsibilities. Treat logs as sensitive: connect --json lifecycle events include local socket addresses and deadlines, even though they carry no payloads or credentials.

/livez checks process liveness only. Cluster /readyz checks admission conditions, but a non-cluster relay always reports ready once serving, even when Redis authority is unavailable and requests return 503 AUTHORIZATION_UNAVAILABLE. Do not use that non-cluster response as a dependency-health guarantee. Neither endpoint proves an end-to-end capability works.

Redis connection diagnostics

Current main reports bounded connection stages and failure classes in serve, activate-first-incarnation, provision-catalog, recovery-observe and recover. Older binaries may report only a generic connection failure.

Redis catalog connection failed; stage=connection_establishment lane=3/6 class=timeout

This example means the initial connection and two lanes opened, then lane three failed. The optional lane number identifies one of six authority connections opened after the initial connection. Recovery commands use the prefix recovery Redis connection failed;. These diagnostics use fixed words rather than URLs, hostnames, credentials or Redis reply text.

Stage or classWhat to check
stage=tls_setupLocal TLS configuration and referenced certificate/key files.
stage=connection_establishmentDNS, TCP, TLS handshake or AUTH; inspect the class.
stage=ping / primary_identityPING or INFO server access and replies.
stage=authority_profile / authority_identityAuthority configuration and deployment-incarnation prerequisites; do not bypass fences.
class=dns / refused / timeout / ioName resolution, listener reachability, connection budget or transport failure.
class=tls_certificate / tls_alert / tlsServer trust, hostname and client certificate requirements.
class=auth / nopermRedis credentials versus permission to run the required command.
class=reply / invalid_reply / run_id_conflict / config / catalogReply shape, Redis run identity, configuration or catalog refusal; retain the stage when reporting.

Each startup or recovery connection gets a 10-second connection budget covering DNS, TCP, TLS and AUTH; subsequent commands have a 2-second deadline. This is not a 10-second bound for the whole startup. Live authority-lane reconnects remain capped at 2 seconds for the entire reconnect, including DNS, by the caller's deadline. Slow cold DNS can still defeat those reconnects; that limitation is open. Source and scoped regression tests were reviewed, not rerun as deployment acceptance.

Redis restart and backup

Current main supports one narrow case: a single non-cluster relay's Redis restarting in place from its own durable AOF, retaining acknowledged writes. It does not cover replica promotion, restored backups or replaced volumes. Cluster Redis restarts and uncertain authority still require the recovery workflow with an external signing authority that is not shipped.

Automatic continuity: the optional top-level relay setting redis_restart_continuity_seconds accepts 1 to 60 seconds and is rejected with [cluster]. The relay must remain running across the Redis restart. It periodically records a token and can rebind the namespace to the new Redis run only when continuity and durability checks pass. Both startup and ongoing checks require appendonly yes, appendfsync always and no-appendfsync-on-rewrite no, with permission for CONFIG GET. The Fly template sets the interval to 5 seconds; this is not a global default.

Do not use continuity with failover or restore. A recent backup or replica may hold the token yet omit later acknowledged revocations. Never weaken the persistence settings at runtime: detection has an interval-plus-deadline window, and a crash inside it can still lose recent writes. A stopped or failing token loop cannot indefinitely authorize a later restart. These checks do not replace operator control of Redis's storage history.

Operator attestation: if the relay did not remain running, or continuity was not enabled, first verify that the same Redis restarted from its own data directory with no restore, volume replacement or replica promotion. Only then use the following command with the same single-relay configuration:

tunnel-relay rebind-redis-run --config /absolute/path/relay.toml --redis-restarted-in-place

The flag is an operator declaration, not an automated proof that data survived. The command preserves the namespace and incarnation and refuses an unbound namespace or cluster configuration. It does not clear a running relay's previously detected continuity mismatch. Do not use it to bypass a restore or lost-data refusal; follow externally approved recovery or provision a genuinely new deployment instead.

Failure classMeaning
run_changedThe stored binding names an earlier Redis run; evaluate the supported in-place restart path.
unboundThe namespace has no incarnation or run binding, including an empty Redis.
continuityThe running relay did not find a permitted continuity token; it keeps refusing that run.
persistenceRequired durability settings were absent or CONFIG GET was refused.

Repository process evidence covers in-place restart/crash and selected lost-data refusals using shipped binaries; it is not hosted deployment acceptance or a new test run here. Devices may lose sessions and reconnect, and owner leases/backoff can delay resumed service. Non-cluster readiness remains insufficient to establish authority health.

Redis backups still use operator tooling. Historical Redis 8.4.0 dogfood evidence found AOF transaction replay failures with the default user disabled and a separate relay ACL user. No least-privilege ACL profile is validated. Test your exact Redis version, persistence and ACL configuration without assuming a saved AOF restores authorization records or weakening authentication. Preserve membership and recovery state.

Reconnect limits

After this process's own session ends, OWNER_BUSY is retried for up to 60 seconds; on a fresh process's first attempt it exits 7. A relay crash can retain ownership for the lease duration, up to 30 seconds. Current main's owner-local device control loop sends WebSocket Pings every 10 seconds and evicts after 30 seconds without any inbound frame, followed by a disconnect hand-off bounded at 5 seconds. These constants are not configurable. The client reconnects on its next attempt, not necessarily at exactly 30 seconds.

Repository evidence records an owner-local cut-path reconnect and a healthy idle session surviving the check. Older relays and devices attached through a non-owner cluster relay are not covered by this fix and can still retain stale ownership; an operator-managed relay restart interrupts its other sessions too. Reconnect does not restore in-flight operations or authorize replay.

A separate source-identified limitation remains: the client's control Pong can be held behind a pending OPEN or a full control queue, then fail its 5-second critical-response deadline and end a healthy session. This was not measured as a runtime occurrence. The liveness fix is not a claim of complete reconnect or saturation acceptance.

Rotation refusals

Scoped dogfood evidence found transient 503 PEER_UNAVAILABLE refusals around data rotation, including on one relay, with retry_after_ms of 250. Respect retry guidance only for a known refused/not-dispatched operation; reconcile any ambiguous side effect before repeating it. Seamless rotation for every capability is not established by this observation.

Current main resumes connector OPEN admission at rotation COMMIT, including the retiring phase, to match the owner. This addresses a separate intermittent 503 DEVICE_REJECTED caused by the connector refusing new work as draining after the owner had resumed admission. Admission closes again if the active data carrier is lost, including during retirement. Source and focused regression tests cover these decisions; they were not rerun for this website review.

Remaining limit: the connector's writer stays frozen until ROTATE_COMPLETE even though new operations can be admitted earlier. If retirement stalls, output may wait for forced completion at the overlap deadline plus handshake grace, 30 + 10 seconds with defaults. This is a source-derived bound, not a measured latency guarantee. A shorter consumer timeout can leave an unknown operation outcome rather than an explicit refusal. Do not replay side effects merely because the response timed out. Complete rotation acceptance remains open.

Admission and cluster limits

After a burst of stream releases, the owner may admit a consumer before the connector has retired those streams from its own capacity count. The consumer can receive a WebSocket 101 upgrade followed by a Close without a typed reason when the connector refuses the OPEN. This remains unresolved; an upgrade alone does not prove that work was admitted by the device.

Current main fixes a stale cached owner epoch after a device reconnects to the same relay: peer routing now binds to the freshly read owner generation rather than an older cached one. Scoped production-gate evidence supports the fix, but some peer-ingress refusals still end without response headers and can fail the shared HTTP/3 connection, interrupting other multiplexed streams. The routing fix removes a common trigger, not the remaining refusal defect. Complete cluster acceptance remains open; these runtime gates were not rerun for this website review.

Queue-saturation tests pin socket buffers only in the fixture. Production kernel buffers add OS-bounded capacity beyond the relay's configured application queues; the test's buffer sizes are not production limits. A graceful WebSocket Close also follows already-buffered records, so cancellation under saturation can take seconds while queued work continues. Do not assume immediate cancellation or blindly replay interrupted operations.

Echo retention limits

Completed finite echoes now have explicit retention cleanup, addressing the earlier failure after 128 requests in one session. Other exits, including RESET, cancellation, authorization invalidation and an expired or disconnected consumer request, can still retain entries. They can exhaust capacity or break a rotation roster. A client reporting an active session is not proof that it can admit new work; automatic replacement of a retention-exhausted session remains planned. Do not increase limits or blindly repeat interrupted operations as a substitute for resolving their outcomes.

Connected but access denied

Check the authenticated principal's tenant membership and device/service/operation grant, local export configuration and policy revision. Some inaccessible resources deliberately appear as not found rather than leaking their existence.

Catalog changes and revocation

The catalog-change CLI adds records and replaces or revokes grants while the relay serves. It does not add a second tenant or renew an existing device certificate. A dry run checks local inputs, not current authority state. Refusals exit 1; a second stop signal can abandon a writing command with exit 130 and an unknown outcome.

Revocation is not retroactive cancellation of completed effects. A grant already admitted can remain authorized for up to five seconds. Device/credential revocation is also detected by session maintenance, which checks up to 64 sessions every 500 ms. That schedule and Redis latency are not an instantaneous global cutoff. Repository evidence measured one device's revocation and terminal credential refusal on reconnect; the live-session close for credential-only revocation was not measured. No revocation runtime tests were rerun for this website review.

Control-path stalls and authorization expiry

The connector buffers stream input while authorization refresh is unconfirmed. If authorization expires, it discards that buffered input even when transport acknowledgements have already removed it from relay replay. Stall tolerance remains limited; transport acknowledgement is not application completion.

Corrected measurements: the earlier claim that a two-second stall lost an echo used an experiment whose actual stall lasted at least five seconds. In the corrected Linux-container experiment, exact two- and three-second stalls each delivered 3 of 3 records; four- and 5.5-second stalls each delivered 2 of 3. These small samples are not a timeout guarantee, and they do not fully explain the earlier hosted failures.

Current main fixes unanswered echo waiters when the connector sends FIN or RESET: the relay produces DEVICE_CLOSED or DEVICE_RESET, with execution unknown for dispatched records and not_dispatched for queued records. Scoped container evidence now records consumer closure as a lapsed stall ends instead of waiting out the old 30-second timeout. This is an echo-path fix, not proof that every capability or network fault delivers a prompt error. Reconcile unknown side effects before retrying.

The connector also skips already-invalidated streams during expiry checks; a focused regression test covers one expiry across five ticks. Internal StreamAuthCounters expose unconfirmed streams, refreshes in flight, buffered input and expired streams in connection status and harness diagnostics, not a new CLI command. Harness hold fixes and these product fixes do not establish complete transport acceptance. Runtime tests were not rerun for this website review; hosted verification remains separate.

Interrupted operation

Distinguish not-dispatched from unknown outcome. Reconcile the application state before retrying writes, clicks or prompts. Do not treat a transport acknowledgement or HTTP 202 as completion.

Reporting a problem

Capture the source revision, platform, selected profile, redacted identifiers, phase and counters. Exclude tokens, private keys, tool payloads, screenshots of private data and user file contents.
